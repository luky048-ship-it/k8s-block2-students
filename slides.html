Проблема: конфигурация внутри образа

# Так делали в блоке 1 (условно):
APP_NAME = "calc-dev"
CALC_PRECISION = 2

Один и тот же образ должен работать везде:

dev
отладка, precision 4
stage
почти бой
prod
бой, precision 2

Если конфиг в образе — под каждое окружение своя сборка. А пересобранный «тот же» образ может оказаться не тем, что тестировали.

Вспомните Artifactory: промоутим биты, а не пересобираем. Здесь тот же принцип.

ConfigMap: что это

Объект кластера: пары ключ-значение (строки) для несекретных настроек.

ConfigMap

CALC_PRECISION=4
→
Pod
приложение читает настройки
kubectl create configmap calc-config \
  --from-literal=APP_NAME=calc-prod -n demo

Подвох: обновление конфигурации

env / envFromvolume (файл)

В задании 1 сами увидите: поменяли ConfigMap — а /config старый. До restart.

Границы ConfigMap

  • до 1 МиБ — это не файловое хранилище
  • только строки; не для паролей — для них Secret
  • живёт в namespace — из другого namespace не виден
  • имя ключа станет именем переменной/файла — выбирайте осмысленно

Secret: пароли в кластере

Тот же формат, но для чувствительного:

kubectl create secret generic db-credentials \
  --from-literal=username=calc_user \
  --from-literal=password=s3cret-pass -n demo
Secret
db-credentials
→
Pod
env: DB_USER, DB_PASSWORD

Подключение — как у ConfigMap: secretKeyRef или том.

base64 — это НЕ шифрование

kubectl get secret db-credentials -o yaml
# data:
#   password: czNjcmV0LXBhc3M=

echo "czNjcmV0LXBhc3M=" | base64 -d
# s3cret-pass  ← читается любым без ключа
  • base64 — кодировка: обратима за секунду
  • магия «шифрования» тут отсутствует — запомните это раз и навсегда

Чем Secret реально защищён

kubectl describe
значения скрыты
RBAC
кто может читать секреты
etcd encryption
если включено админом
  • но: kubectl get secret -o yaml тому, у кого есть доступ, покажет всё — доступ к API = доступ к секретам
  • поэтому манифесты с секретами не коммитим в git; в бою — Vault, Sealed Secrets, облачные хранилища

Service: зачем стабильная точка входа

Под пересоздался → сменился IP. А обращаться надо по постоянному адресу.

Service
calc-service
IP постоянный
→
Pod 10.1.0.7
Pod 10.1.0.8 ✕ умер
Pod 10.1.0.9 новый

Service находит «свои» поды по selector (labels) — состав может меняться, точка входа остаётся.

Как Service выбирает поды

Service
selector: app=calc-app
⇄
Pod
labels: app=calc-app ✓
Pod
labels: app=other ✗
  • совпал label → под в списке endpoints сервиса
  • опечатка в label → сервис «пустой», запросы в никуда
  • проверка: kubectl describe svc → Endpoints

NodePort: порт на каждом узле

ноутбук
→
узел :31234
→
Service :80
→
Pod :5000
  • кластер открывает порт 30000–32767 на всех узлах сразу
  • для отладки и учебных стендов; в проде так не ходят
  • в minikube: minikube service calc-service -n demo --url

LoadBalancer: облачный балансировщик

интернет

публичный IP
→

  • в облаке (AWS/YC/GCP) тип LoadBalancer заказывает настоящий балансировщик с публичным адресом
  • в minikube его нет (эмулируется minikube tunnel)

Заметьте: NodePort и LoadBalancer строятся НАД ClusterIP — он есть всегда.

Нюанс minikube на macOS

  • с docker-драйвером узел живёт в контейнере, его IP недоступен напрямую с macOS
  • поэтому minikube service --url поднимает туннель на 127.0.0.1 — терминал с ним должен оставаться открытым
  • это не поломка, это особенность драйвера

Ingress: человеческий адрес

Проблема: 192.168.49.2:31234 — не адрес для людей. А приложений много, и портов 30000+ на всех не хватит.

Ingress-контроллер
nginx внутри кластера
+
Ingress-правила
calc.local → calc-service:80

Контроллер — обратный прокси; Ingress (объект) — его конфигурация.

Полный путь запроса

браузер
calc.local
→
/etc/hosts
calc.local → IP minikube
→
ingress-контроллер
смотрит Host
→
calc-service
→
Pod
  • сервис за Ingress остаётся ClusterIP — NodePort не нужен
  • в жизни вместо /etc/hosts — настоящий DNS
  • один контроллер обслуживает много приложений и хостов

Один Ingress — много приложений

ingress-контроллер
calc.local → calc-service
web.local → web-service
api.local → api-service

Маршрутизация по имени хоста (Host-заголовок) или по пути (/api → один сервис, / → другой). Челлендж задания 6 — именно про это.

Итоги

  • образ неизменен, конфигурация — снаружи: ConfigMap и Secret
  • env — при старте пода; файл — обновляется сам
  • base64 — кодировка, а не защита; защита Secret — в RBAC
  • ClusterIP внутри, NodePort для отладки, Ingress — для людей
  • путь запроса вы теперь можете нарисовать по памяти
